## 一、快速启动

### 方式一：一键启动（Windows，推荐）

项目目录下双击 **`一键启动.bat`**，脚本自动检查 Node.js → 安装依赖 → 初始化数据库 → 启动服务并打开浏览器。

### 方式二：Docker 容器化（推荐服务器部署）

```bash
# 在你的 Linux 服务器或 WSL 里，项目目录下：
docker compose up -d --build
# 首次启动会自动建库（种子管理员 admin/admin123）
# 数据保存在 ./data/ 目录，升级镜像不会丢数据
# 停止：docker compose down
# 查看日志：docker compose logs -f
```

详见第五章"容器化部署详解"。

### 方式三：手动命令行

```bash
npm install           # 首次运行
npm run db:init       # 首次运行，初始化数据库
npm run dev           # 开发模式，http://localhost:3777
# 生产模式（更快更稳）：
npm run build && npm start
```

## 三、渠道管理

### 添加渠道

1. 左侧点击 **"渠道管理"** → 右上角 **"+ 新建渠道"**
2. 填写以下信息：

| 字段 | 说明 | 示例 |
|------|------|------|
| 名称 | 自定义标识 | DeepSeek 官方 |
| 供应商 | 用于列表分组展示（可选）；同名供应商的渠道归入同一分组，留空则按名称前缀自动分组 | 商汤 |
| 类型 | 供应商协议类型 | OpenAI 兼容 / Anthropic / Gemini |
| Base URL | 供应商 API 地址（到域名/IP） | https://api.deepseek.com |
| API Key | 从供应商获得的密钥 | sk-xxxx |
| 支持的模型 | 支持哪些模型，每行一个 | deepseek-chat |
| 模型映射 | 对外模型名 → 上游真实模型名（可选） | `{"my-gpt":"deepseek-chat"}` |
| 代理地址 | 被墙的供应商走代理（可选） | http://127.0.0.1:7890 |
| 优先级 | 数字越大越优先（选路时优先生效） | 10 |
| 权重 | 同优先级内按权重随机 | 1 |

3. 填写后点 **"保存"**，然后点右侧 **"连通测试"** 验证渠道是否可用

### 获取模型（一键拉取列表）

1. 新建/编辑渠道时，填好 Base URL 和 API Key 后
2. 点 **"获取模型"** 按钮 → 自动拉取该供应商的全部可用模型
3. 在弹出的**勾选列表**里勾选你需要的模型，点 **"确定"** 自动填入文本框
4. 列表里每行右侧有 **"测试"** 按钮，可单独测试某个模型通不通；顶部 **"全部测试"** 一键测试所有

### 模型映射（可视化 KV 编辑器）

当你想让调用方用你的统一模型名，而不是供应商的原始名时使用：

```
调用方请求: my-gpt
        ↓
网关查映射: my-gpt → deepseek-chat
        ↓
实际转发: deepseek-chat
        ↓
响应返回: model 字段还原为 my-gpt（调用方无感知）
```

在渠道表单的"模型映射"区域，点 **"+ 添加映射"** 逐行添加，左侧填对外名、右侧填上游名，保存时自动校验。

### 渠道代理

OpenAI 等被墙的供应商，填代理地址：

- **HTTP 代理**：`http://127.0.0.1:7890`（Clash/V2Ray 常用）
- **SOCKS5 代理**：`socks5://127.0.0.1:1080`
- 支持用户名密码：`http://user:pass@proxy:8080`

配置后，该渠道的**所有请求**（对话转发、连通测试、获取模型）都走代理。未配置的渠道不受影响。

### 复制渠道

渠道列表的操作列 **"复制"** 按钮，把该渠道的完整配置（含 API Key）带入新建表单，名称自动加"副本"后缀，方便创建同供应商的多渠道负载均衡。

### 供应商分组展示

同名（或同前缀，如"商汤-02""商汤 v3"与"商汤"）的渠道在列表中自动聚在一起，多于一个渠道的分组会显示一条分组标题行（组名 + 渠道数），同一供应商的多个账号不再被其他渠道隔开。归档页同样生效。

如果渠道名称与供应商对不上（比如都是"中转站"开头的名字但实际是两家供应商），在渠道表单里**显式填写"供应商"字段**即可精确归组——填了供应商的渠道优先按它分组，名称列会显示一个供应商徽标；留空则按名称前缀自动分组，老渠道无需补填。

## 四、API 令牌

### 创建令牌

1. 左侧 **"API 令牌"** → 填写名称 → 可选额度上限（美元）和有效期（天）
2. 点 **"创建令牌"** → 完整 Key 只显示一次，立即复制保存
3. 如果没来得及复制，点列表里的**眼睛图标**可随时查看，点**复制图标**复制到剪贴板

### 查看令牌 Key

每行 Key 显示为 `sk-xxxx••••••••`，点右侧**眼睛图标**查看完整 Key，再点隐藏。**复制图标**一键复制到剪贴板。

### 使用 API 地址

令牌页顶部显示 **API 接口地址**（如 `http://localhost:3777/v1`），调用方把 OpenAI SDK 的 `base_url` 设为该地址即可。

### 调用示例

```bash
curl http://localhost:3777/v1/chat/completions \
  -H "Authorization: Bearer sk-你的令牌" \
  -H "Content-Type: application/json" \
  -d '{"model":"deepseek-chat","messages":[{"role":"user","content":"你好"}],"stream":true}'
```

Python OpenAI SDK：

```python
from openai import OpenAI
client = OpenAI(api_key="sk-你的令牌", base_url="http://localhost:3777/v1")
response = client.chat.completions.create(model="deepseek-chat", messages=[{"role":"user","content":"你好"}])
print(response.choices[0].message.content)
```

## 五、容器化部署详解

### 前提条件

- 安装了 Docker（Linux 或 WSL 2）
- 项目已克隆到本地

### 方式一：docker compose（推荐）

```bash
# 1. 进入项目目录
cd /path/to/api调用

# 2. 构建并启动
GATEWAY_SECRET=你的强随机密钥 docker compose up -d --build

# 3. 验证
curl http://localhost:3777/login
# 返回 200 即正常

# 4. 查看日志
docker compose logs -f
```

### 方式二：纯 docker

```bash
# 1. 构建镜像
docker build -t myapi:latest .

# 2. 创建数据目录
mkdir -p /data/myapi

# 3. 运行容器
docker run -d --name llm-gateway --restart unless-stopped \
  -p 3777:3777 \
  -v /data/myapi:/app/data \
  -e GATEWAY_SECRET=你的强随机密钥 \
  myapi:latest

# 4. 验证
docker logs -f llm-gateway
```

### 数据迁移（旧数据卷升级）

如果已有旧数据卷（数据库文件已存在），升级后需要补一次**数据库迁移**（新版本可能新增了列）：

```bash
docker compose exec myapi npx tsx scripts/init-db.ts
```

该命令是安全的（幂等），只添加缺失的列，不影响已有数据。

### 生产环境建议

- 宿主机挂载目录（`/app/data`）要定期备份
- 反向代理（Nginx/Caddy）绑定 443 端口，**流式响应必须关闭代理缓冲**：
  ```nginx
  location / {
    proxy_pass http://127.0.0.1:3777;
    proxy_buffering off;
    proxy_cache off;
  }
  ```
- 进程守护：`docker compose up -d` 已自带 `--restart unless-stopped`

### 性能说明

- 当前是 Node.js 直跑，非 Go 实现，单机吞吐量取决于上游响应速度
- 瓶颈通常在上游 LLM 供应商，而非网关本身

## 六、失败重连规则

当上游返回错误状态码时，网关在切换渠道前可以**按规则重试**。

### 配置入口

左侧 **"重试规则"**（管理员可见）

### 规则说明

| 字段 | 说明 | 默认值 |
|------|------|--------|
| 错误代号 | 上游 HTTP 状态码（0 = 全局默认） | 429 / 500 / 0 |
| 重试次数 | 同一渠道上最多重试几次 | 3 / 2 / 1 |
| 首次重试等待 | 第一次失败后等多久再重试 | 2000ms / 1000ms / 1000ms |
| 最大等待时间 | 翻倍增长的上限 | 10000ms |
| 抖动比例 | 实际等待 = 计算值 × (1±抖动) 随机数 | 0.1（10%） |

**命中规则**：精确匹配错误代号 → 全局默认（代号 0）→ 不重试

**等待时间算法**：第 n 次重试等待 = `首次等待 × 2^(n-1)`，上限 `最大等待时间`，再乘以 `(1±抖动)` 的随机系数。

**示例**：429 规则（3 次/首等 2s/上限 10s/抖动 10%）
- 第一次失败 → 等 2s 重试（实际 ±10% 随机）→ 再失败
- 第二次 → 等 4s → 再失败
- 第三次 → 等 8s → 再失败
- 重试耗尽 → 切换下一渠道（若属于 429/5xx 等可切换的错误）

## 八、备份还原

### 适用场景

- 换电脑 / 迁移部署
- 升级前存档

### 导出

1. 左侧 **"备份还原"** → **"导出备份文件"**
2. 下载的 JSON 文件包含：**全部渠道（含明文 API Key）**、用户、令牌（含哈希）、重试规则、模型定价
3. ⚠ 文件包含所有供应商的明文密钥，请妥善保管

### 还原

1. 在新机器上部署好项目，启动服务
2. 用管理员登录，进入"备份还原"页面
3. 选择备份文件 → 确认概要 → 点 **"确认还原（覆盖现有配置）"**
4. 还原后所有用户需重新登录

## 九、仪表盘解读

### 指标卡

6 张彩色卡片：总调用次数、成功率、累计消费、近 24h 调用、近 24h 消费、总 Tokens（完整数字，无 M 缩写）

### Token 用量统计

三块排版：

| 输入块 | 输出块 | 总 Tokens 块 |
|--------|--------|-------------|
| 输入总量 | 输出总量 | 总和 |
| 缓存命中（绿色）| 推理（品红）| = 输入 + 输出 |
| 缓存未命中（橙色）| 回答（天蓝）| |

### 近 14 天趋势

三个标签页（VChart 图表库）：

- **趋势**：按模型堆叠的平滑面积图，可选调用次数 / Tokens / 消费金额；可切换按天 / 按小时；图例点击隐藏/显示模型
- **占比**：各模型调用次数环形饼图
- **排名**：模型调用次数 Top 10 条形图

### 模型列表

所有启用渠道的模型搜索列表，点击进入**模型详情页**（查看供应商、按渠道统计、Token 明细、分页调用记录）

## 十一、常见问题

### 127.0.0.1 打不开 / 登录不了？

这是 **开发模式**（npm run dev）的已知问题，已修复。使用 `http://localhost:3777` 即可。生产模式（build + start）或 Docker 部署无此问题。

### 数据存在哪里？

`data/gateway.db` 文件（SQLite）。换电脑时使用"备份还原"功能迁移。

### 想换主密钥（GATEWAY_SECRET）？

**注意**：更换后已保存的渠道密钥会被清空，需要重新填写每个渠道的 API Key。建议换密钥前先导出备份，换完再还原。

### 怎样升级？

```bash
# 本地：git pull → npm install → npm run build → 重启
# Docker：git pull → docker compose up -d --build
```
